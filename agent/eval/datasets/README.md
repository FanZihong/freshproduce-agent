# 检索评测集说明

`qa_golden.jsonl` 每行一条，字段：

| 字段 | 说明 |
| --- | --- |
| id | 用例编号 |
| question | 用户当前提问（多轮用例里是追问） |
| context | 多轮上下文，`{"last_question": ..., "product": ...}`，单轮为 null |
| relevant_chunk_ids | 标准答案，命中其中任意一条即算相关 |
| case_type | `direct` 单轮 / `multi_turn` 多轮指代 |
| note | 备注，说明该用例考察什么 |

设计约束：

1. 30 条用例覆盖 15 个关键 chunk，每个 chunk 至少 2 种问法；
2. 其中 5 条是多轮用例，考察指代消解；
3. 出现"同一问题有两处等价答案"时（例如退款到账时效同时写在政策与 FAQ），
   `relevant_chunk_ids` 会同时列出，避免把正确答案判成错。

评测集与开发调试集分离：调检索参数时不看这 30 条以外的临时查询，
避免把参数调成"只对评测集有效"。

# 端到端对话评测集说明

`dialogues_golden.jsonl` 每行一段完整对话（不是单句），用于评测 agent 是否**真的把事办成**。

| 字段 | 说明 |
| --- | --- |
| id | 用例编号（dg-XX） |
| scenario | 场景名，一句话说清这条测什么 |
| chain | 走哪条链路：order / claim / faq / handoff / fallback / multi / boundary |
| category | `core` 主链路 / `noise` 真实口语变形 / `boundary` 模糊与放弃场景 |
| turns | 逐轮用户输入；每轮可带 `expected_tool`（该轮应调用的工具）或 `expected_slot`（该轮应填的槽位） |
| expected_goal_resolved | **这段对话结束时，用户最初的诉求是否真被办成**（不是"有没有回复"） |
| expected_handoff | 是否应当转人工 |
| resolution_criteria | 判定标准，用一两句话说清"什么算解决" |
| check | 机器可读的判据（见下） |
| requires_env | 只在特定配置下有效的用例，例如 `{"INTENT_BACKEND": "local"}` |
| note | 备注：设计意图、已知缺口、首跑校准点 |

`check` 的字段语义（判分脚本按这个执行）：

| 键 | 语义 |
| --- | --- |
| tools | 整段对话累计调用过的工具名集合（顺序不限） |
| reply_contains | 最后一轮回复里必须**全部**出现的子串 |
| reply_contains_any | 最后一轮回复里至少出现**其中一个**子串 |
| handoff_summary_contains | 交接摘要里必须出现的子串 |
| branches | 执行过的分支集合（用于多意图对比） |

判定标准写在**行为层**（用了哪个工具、有没有引用、有没有转人工、赔付金额对不对），
而不是抠话术措辞——话术会改，行为契约不该变。少数必须检查文本的地方，都用代码里的稳定常量
（如「参考来源」「超出了售后服务的范围」「签收人为本人」）。

几个刻意的约定：

1. **碎片句单独归类**：`dg-27`～`dg-29` 是缺上下文的真实碎片（JDDC 风格），
   它们与可判样本分开统计，不混进"目标解决率"——否则会把数据缺陷算成模型能力问题
   （这条经验来自意图层的 kappa 与域外误杀两次踩坑）。
2. **同句对照**：`dg-24` 与 `dg-25` 是同一句话、只差 `INTENT_MULTI_STRATEGY`，
   对比时只动一个变量。
3. **首跑校准点**：`dg-14`、`dg-15` 的知识库命中情况需要首跑后确认，
   如果实际是"无据转人工"，就按真实结果改判，而不是迁就预期。
4. **已知覆盖缺口**：每个下单金额都远小于自动赔审上限（200 元），所以
   「赔付金额超限 → 转人工确认」这条降级路径**无法用现有模拟订单触发**。
   要覆盖它，需要加一条金额 > 200 的模拟订单，或临时调小上限做定向测试。
